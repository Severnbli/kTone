# Decision log

## 2026-11-08 – MVP architecture

- **Decision:** Rust core (`core/`) with pitch detection (MPM) and music theory, exposed to the web via `wasm-bindgen` (`wasm/`). React + TypeScript + Vite PWA in `web/`. Docker Compose for the dev environment and the prototype.
- **Why:** one DSP/theory implementation reusable later in native apps; MPM is fast, accurate on voice and simple to implement without allocations.
- **Audio path:** `AudioWorklet` captures mic samples and posts them to the main thread; the main thread runs the WASM analyzer on 2048-sample frames with a 512-sample hop. Running WASM inside the worklet is a later optimization.
- **Alternatives:** YIN (similar quality, slightly more expensive), CREPE/SwiftF0 (more robust, much heavier – possible future option).

## 2026-11-08 – Pitch detector details

- **Decision:** MPM with NSDF computed via an in-house radix-2 FFT autocorrelation (frame 2048 padded to 4096), key-maxima threshold 0.9, parabolic interpolation. Tracker: RMS and clarity gates, 5-frame median (3 since the 2026-11-09 latency work) in the semitone domain, octave guard (a jump of 1–2 octaves must persist for 4 frames), 30-cent hysteresis on the displayed note, history reset after 4 silent frames.
- **Why:** no runtime dependencies, no allocations per frame, sub-cent accuracy on clean signals, no octave errors in tests.
- **Trade-offs:** a real octave leap shows up after ~40 ms; low notes (~E2) in heavy noise can be off by up to ~7 cents.

## 2026-11-08 – Note spelling rule

- **Decision:** each key maps the 12 pitch classes to one spelling. Diatonic notes use the key spelling; minor keys spell raised 6th and 7th as raised degrees; other chromatic notes pick the spelling with the smaller accidental, ties go to raising in sharp keys and lowering in flat keys; C major / A minor use C♯ E♭ F♯ G♯ B♭.
- **Why:** deterministic, readable, avoids double accidentals for chromatic notes.

## 2026-11-08 – Engine loading

- **Decision:** the web app loads the WASM package through `import.meta.glob`, so builds and unit tests work without Rust; when the package is missing or fails to load, the TS mock engine is used. Analysis runs on the main thread; the AudioWorklet only captures audio.

## 2026-11-08 – Offline support and service worker updates

- **Decision:** a small in-repo Vite plugin (`web/sw/precache.ts`) writes `dist/sw.js` at build time: a precache manifest (every emitted file plus the public files, minus source maps and the worker itself) followed by the worker source `web/sw/sw.js`. The cache is named `ktone-<version>`, where the version is a SHA-256 over all precached paths and contents, so every build gets a fresh cache and a byte-different `sw.js`. Paths are relative to the worker scope, so a non-root Vite `base` works.
- **Fetch strategy:** precached files and all navigations (SPA fallback to `index.html`) are served cache-first from the active build's cache; other requests are not intercepted. A page therefore always runs one consistent build: bundles, `pitch-worklet.js` and the `.wasm` come from the same cache.
- **Update flow:** the new worker precaches the new build in the background and waits; it does not call `skipWaiting` on its own, so the open page (maybe mid-exercise) is never switched under the user. On the next launch `src/registerSW.ts` sees the waiting worker, sends `SKIP_WAITING` and reloads once on `controllerchange`, right at startup. On activate the worker deletes older `ktone-*` caches and claims the clients. The app also calls `registration.update()` when it returns to the foreground, for long-lived installed PWAs.
- **Server:** nginx serves `/assets/` (hashed) as `immutable` for a year and everything else (`index.html`, `sw.js`, the worklet, the manifest, icons) as `no-cache`. The precache also fetches with `cache: 'reload'` so a stale HTTP cache cannot leak into a new build's cache.
- **Alternatives:** Workbox / `vite-plugin-pwa` (heavy dependency and generated code for what is ~100 lines here); network-first navigations (fresh HTML online, but an old worker would then mix a new `index.html` with an old cached worklet); `skipWaiting` on install (immediate updates, but an open page could get a worklet from a different build); a "new version, reload?" prompt (needs UI in `App.tsx`, can be added later on top of the same waiting worker).
- **Caveats:** an update takes effect on the second launch after deploy (one to download it, one to apply it). With several tabs open, the tab that applies the update reloads, the others keep running and are claimed by the new worker.

## 2026-11-08 – Recorded voice test fixtures

- **Decision:** test the pitch tracker on five short excerpts (about 11 s, under 1 MB in total) from VocalSet 1.2 (Zenodo, DOI 10.5281/zenodo.1442513, CC BY 4.0): bass and baritone long tones, a soprano F5, a bass C4 with strong vibrato, a sung phrase with consonant onsets and an ascending scale. Clips live in `core/tests/fixtures/voice/` with `SOURCES.md` (attribution, cuts, ground truth); tests in `core/tests/pitch_voice.rs` read them with `hound` (dev-dependency only).
- **Why:** VocalSet is recorded by professional singers of known voice types, sung from a published score (so every note has a stated target), is mono 16-bit 44.1 kHz WAV, and its license allows redistribution with attribution. Single files can be extracted from the Zenodo archive with HTTP range requests, so the whole 2–6 GB archive is not needed.
- **Ground truth:** the note from the score, confirmed and refined (median pitch, note boundaries) by an independent offline YIN analysis with a spectral octave check, never by the detector under test.
- **Alternatives:** freesound.org CC0 vocals (no stated target notes, quality and licenses vary per upload), datasets under NC licenses such as Children's Song Dataset or GTSinger (not compatible with an open-source repository).

## 2026-11-08 – Judge accuracy by the vibrato center

- **Decision:** `PitchTracker` reports a vibrato center (`center_midi`, `center_cents` relative to `stable_midi`): a triangular-weighted moving average (weights 1, 2, .., 2, 1) of the accepted, octave-guarded but unmedianed estimates over `CENTER_WINDOW_SECS` = 300 ms. The window is configured in frames (`TrackerConfig::center_window`, default 28 for hop 512 at 48 kHz); `TrackerConfig::for_hop(sample_rate, hop)` sizes it for other rates. The center history restarts when `stable_midi` changes and with the rest of the smoothing state (pause of 4 frames, `reset`, A4 change). The WASM output appends `centerMidi` and `centerCents` (slots 12 and 13, 14 fields). The cents gauge needle, readout and zone follow `centerCents`; the pitch curve draws the raw pitch and colors segments by the center-based zone.
- **Why:** a ±40 cent vibrato at 5–6 Hz made the per-frame zone flick between green and red, although AGENTS.md says vibrato is judged by its center. A triangular window is two cascaded box filters: on synthetic ±40 cent vibrato the residual is about 5 cents at 4.5 Hz, 3 cents at 5 Hz and 1 cent or less from 5.5 Hz up, where a plain 250 ms average leaves up to about 9 cents. Restarting on a new stable note lets the needle settle on the new note about 60 ms after a leap.
- **Trade-offs:** the needle lags slow pitch drifts within a note by about half the window (~150 ms) – a calm needle was preferred over an instant one. Right after an onset or a note change the window holds only a few frames, so the center briefly follows the vibrato until it refills (~300 ms). A vibrato wide enough to cross the hysteresis band restarts the center on every crossing.
- **Alternatives:** plain moving average (cheaper, but leaves too much vibrato), low-pass IIR (no allocation either, but its long tail drags the previous note and needs explicit resets anyway), peak/valley tracking of the vibrato cycle (more precise for regular vibrato, fragile for irregular singing).

## 2026-11-08 – Mobile lifecycle: wake lock and audio interruptions

- **Decision:** the app reacts to phone-style interruptions with a few simple rules, implemented in `web/src/audio/lifecycle.ts`, `mic.ts`, `pitchEngine.ts`, `wakeLock.ts` and `DroneControls.tsx`:
  - **Screen Wake Lock** is held while the mic is running or the drone is playing, released otherwise, and re-requested when the page becomes visible again (the browser drops it when hidden). Missing API or refused requests are ignored.
  - **Mic track ended** (device unplugged, permission revoked, mic taken by another app): the engine stops and the UI says the mic was disconnected; "Start" starts a fresh session.
  - **Mic paused** (`AudioContext` `suspended` or Safari `interrupted`, or a muted track): the UI shows a "paused" state. While the page is visible the engine makes one automatic `resume()` attempt (immediately, or when the page becomes visible). If that fails, a "Resume" button appears; it is a user gesture, so it resumes the context, or restarts the mic if resuming the old session is not possible.
  - **Background:** after 60 s hidden the mic is stopped (freeing it for other apps) and the UI says so; coming back sooner changes nothing.
  - **Drone:** its own context follows the same rules: one automatic resume while visible; if that fails, the drone turns off with a short message, and a tap restarts it; 60 s hidden stops it.
  - `resume()` attempts are capped at 1 s, because iOS can leave the promise pending outside a user gesture.
- **Why:** before this, the app silently stopped producing frames while the UI still said it was listening. Automatic recovery covers the common short interruptions; anything that needs a gesture gets an explicit button; long background stays do not hold the mic.
- **Testability:** page visibility, the wake lock API, the mic starter and the drone's `AudioContext` are injected, and the track/context event mapping is a pure function (`watchMicState`), so all rules are covered by Vitest with fakes; e2e checks a real suspended context and an ended track in Chromium.
- **Alternatives:** stopping the mic as soon as the page is hidden (loses the session on a quick app switch); never stopping in the background (keeps the mic indicator on and blocks other apps); auto-retrying resume in a loop (useless on iOS without a gesture, wastes battery).

## 2026-11-08 – Input level meter, level hints and microphone choice

- **Decision:** the web side measures the raw input on every analysis frame (2048 samples, every 512), whether or not a pitch was found, in `web/src/audio/level.ts`: RMS in dBFS (digital silence is −Infinity) and the linear peak, allocation-free. `PitchEngine` feeds a `LevelStore` that the meter reads imperatively, like the cents gauge; React re-renders only when the hint changes.
- **Meter:** RMS on a −70..0 dBFS bar under the cents gauge, with a marker at the analyzer gate. The gate is the core's `rms_threshold` 0.005 (about −46 dBFS), kept as one constant (`ANALYZER_GATE_RMS`) that the meter and hints take as a parameter, so a future noise calibration can pass a measured value instead. _Superseded 2026-11-09: the gate and floor now come from the analyzer, see "Automatic noise gate"._
- **Hints** (time hysteresis, so they do not flicker):
  - _Too quiet_: no pitch while the RMS is between the noise floor (−60 dBFS) and the gate, uninterrupted for 1 s. (_Superseded 2026-11-09: the floor is measured, see "Automatic noise gate"._)
  - _Too loud_: a sample at or above 0.98 (about −0.2 dBFS) keeps a "clipping" condition true for 250 ms; the hint shows once that has held for 300 ms.
  - A shown hint disappears after its condition has been gone for 1 s, and at once when listening stops or is suspended.
- **Microphone choice:** a picker in the settings, filled from `enumerateDevices()` (audio inputs only, Chrome's `default` alias dropped, unnamed inputs shown as «Микрофон N», a note while the browser hides the list before permission), refreshed on `devicechange`. The choice is saved as `micDeviceId` (`''` = system default; any non-string or a string over 256 chars falls back to `''`). `startMic` asks for `deviceId: { exact }` with all voice processing still off; if that device is gone (`OverconstrainedError` or `NotFoundError`) it retries once with the system default. The saved id is kept even when the device is missing (a USB mic that comes back is used again); the picker then shows the default with a note. Changing the device while listening restarts the mic session without going idle.
- **Why:** before this, a too-quiet singer saw only "silence" with no clue why; a level meter with the gate marker shows how far off the input is. Exact `deviceId` makes the choice binding instead of a hint the browser may ignore; the fallback keeps a stale id from breaking Start.
- **Alternatives:** measuring in the worklet (more plumbing for no gain at a 512-sample hop); reusing `PitchFrame.rms` (only reported for voiced frames); dropping the stale id from settings (loses the choice when a device is briefly unplugged); `deviceId` as an ideal constraint (silently opens another device).

## 2026-11-08 – Drone filter

- **Decision:** when the app drone plays, `PitchTracker::set_drone(hz, filter)` checks every frame whose detected pitch is within `drone_tolerance_cents` = 15 cents of the drone or one octave of it. `Mpm::periodic_residual` removes the drone partials (1, 2, 6 and 10 times the drone: the sine plus the triangle's 1st, 3rd and 5th harmonics) and DC by a least-squares fit of amplitude and phase, then measures what is left at the detected period: `periodic` = 2·Σ r(t)·r(t+T) / Σ (x(t)² + x(t+T)²) and the residual's own `clarity` = 2·Σ r(t)·r(t+T) / Σ (r(t)² + r(t+T)²). The fit runs twice, at the nominal drone pitch (exact, robust to noise) and at the measured one (absorbs glides and clock differences); if either leaves `periodic` < `drone_voice_energy` = 0.001 (-30 dB) or `clarity` < `drone_voice_clarity` = 0.5 (the residual is noise), the frame is drone leakage. `drone_leak()` reports it; with the filter on the frame is unpitched. When a frame on the drone pitch itself leaves a residual with clarity ≥ 0.9 at half the period (odd harmonics about 13 dB below the even ones), the singer is an octave above the drone and the pitch is doubled: a louder drone makes the mixture repeat at the drone period, which used to show such a singer an octave low. The setting `droneFilter` (default on) switches the filter off; the leak flag is reported either way, and the UI shows a headphones hint once leaking frames have kept coming (gaps under 500 ms) for 1.5 s, hiding it 500 ms after the last one. WASM: `Analyzer.setDrone(hz, filter)` (hz ≤ 0 = off) and the `droneLeak` getter; TS: `Analyzer.setDrone(hz | null, filter)` and `droneLeak`, with a port in the mock engine (`droneCheck.ts`). Setting the drone never resets the tracker.
- **Why:** the mic runs without echo cancellation, so over speakers the silent singer was shown "hitting" the tonic. A singer on the tonic must still be heard, and the only thing that tells them apart is timbre: the leaked drone is the known partials plus noise, a voice also has the other harmonics (3, 4, 5, 7, …) and jitter that the fit cannot remove. Measured on synthetic signals (`core/tests/pitch_drone.rs`, drones D2, C3, D3, A3, E4, C5 rendered like `drone.ts` incl. the Web Audio biquad, room reflections and noise): the leaked drone through a speaker, with about 1 % distortion, through a small speaker that loses the fundamental, and at 17 dB SNR just above the RMS gate is never shown (0 false accepts) and flagged in 100 % of frames; its `periodic` is ≤ 3·10⁻⁴ (typically 10⁻⁵). Voices (bright, "a", dark "u") on the drone pitch, an octave above and below: 0 % false rejects 6 dB above the drone, at most 2.3 % (dark "u") at the same level; a ±40 cent vibrato on the tonic: 0 %. Notes away from the drone are never checked, so the output is unchanged for them.
- **Trade-offs:** speaker distortion is indistinguishable from voice harmonics: above about 4 % third-harmonic distortion (seen at E4–C5 and D2 in the tests) the leak is shown again – the hint still explains why. A nearly sinusoidal voice on the tonic that is quieter than the leak can be rejected. The filter does not fix the other effect of a loud leak: a voice a fourth, fifth or sixth from the drone at a similar level drops below the clarity gate with or without it. The check costs two small (17×17 with the envelope terms below) least-squares fits per drone-pitched frame, a few times the work of the MPM FFTs, and nothing for other frames.
- **Alternatives:** harmonic-to-fundamental ratio from the MPM spectrum (needs a window and fails below about C3, where the 23 Hz bins cannot separate the harmonics), clarity close to 1 (a steady voice gets there too), subtracting the drone before detection (would also rescue the other intervals, but changes every frame and the latency budget; a good follow-up), learning the leak level while the singer is silent and accepting energy above it (more robust for quiet singers, more state).

## 2026-11-08 – Drone onsets: envelope terms and digitally silent frame edges

- **Decision:** the drone fit lets every partial's amplitude change linearly over the frame (`ENVELOPE_TERMS` = 2: `cos`, `sin`, `u·cos`, `u·sin` with `u` = -0.5..0.5 over the frame). Independently of the drone, `PitchTracker` treats a frame that starts or ends with 16 or more digitally silent samples (|x| ≤ 10⁻⁶) as unpitched. Both are mirrored in the mock engine. The UI still shows a new note from its first accepted frame.
- **Why:** the drone e2e test failed in CI but not for the author (who most likely ran it without the WASM build, i.e. on the mock): with the real engine, the very first frame after the mic starts was shown as «до», and NoteDisplay keeps the last note, so one frame was enough. It was not a race – `setDrone` reaches the analyzer before the first frame. Chromium's fake capture (and real devices while they warm up) deliver exact zeros first, so the first frames are zeros followed by the drone. Such a gated frame both biases the MPM estimate (18 cents in a core test, outside the 15 cent tolerance) and leaves the step in the fit residual, periodic at the drone pitch, i.e. "voice". The same flaw showed up for real use: with a constant-amplitude fit, about 20 frames of the drone's 400 ms attack and 300 ms release were shown as a sung note (`drone_attack_and_release_are_never_a_note`). A linear envelope models those ramps exactly and volume changes closely; silent edges carry no sound and only occur at stream start or dropouts, where skipping the up to 4 partly silent frames (~45 ms) costs nothing.
- **Trade-offs:** the fit is about 3.5 times more work (still only on drone-pitched frames). The envelope terms also absorb a small frequency offset of a pure sine, but a voice is recognized by its other harmonics, and every existing voice test passes unchanged. A real voice that starts right after digital silence is shown up to 4 hops later.
- **Alternatives:** requiring several consecutive voiced frames in NoteDisplay before showing a new note (hides any single stray frame, but adds 1–2 hops of latency to every note against a 30 ms target and treats the symptom; not needed once the filter rejects every onset frame), relaxing the e2e test (would hide a real product bug), trimming the silent edges and fitting only the rest (the biased pitch estimate still fails the tolerance check).

## 2026-11-09 – Latency: how it is measured, and the baseline

- **Decision:** latency is measured in audio time by `core/tests/pitch_latency.rs`: a synthetic voice (4 harmonics, phase-continuous) steps between two notes; frames of 2048 every 512 samples at 48 kHz, four onset positions relative to the hop grid. A frame's result exists once its newest sample has arrived, so the delay of a frame is `frame end - onset`. Reported (mean / max over the alignments, ms), each "for good", i.e. from that frame on: (a) `midi` within 50 cents of the new note, (b) `stable_midi` is the new note, (c) the center within ±10 cents of it. Run it with `cargo test -p ktone-core --test pitch_latency -- --nocapture`. The web app adds the rest of the path, shown by the `?debug` overlay: input buffering (the worklet posts 512-sample blocks, so a frame is analyzed as soon as its last block arrives), message passing, the analysis itself, and up to one display frame (~8 ms on average at 60 Hz). `baseLatency`/`outputLatency` of the `AudioContext` describe the output side; browsers do not expose the input latency, typically 5–20 ms.
- **Baseline** (frame 2048, 5-frame median, 30 cent hysteresis, 300 ms center; vibrato ±35 cents at 5.5 Hz):

  | step | (a) midi | (b) stable | (c) center |
  | --- | --- | --- | --- |
  | bass semitone up (A2→B♭2) | 49 / 53 | 60 / 64 | 60 / 64 |
  | bass fourth down | 63 / 67 | 63 / 67 | 63 / 67 |
  | bass E2 → G2 | 60 / 64 | 60 / 64 | 60 / 64 |
  | tenor semitone down | 49 / 53 | 60 / 64 | 60 / 64 |
  | tenor third up | 57 / 61 | 57 / 61 | 57 / 61 |
  | tenor fifth up | 60 / 64 | 60 / 64 | 60 / 64 |
  | tenor octave up | 73 / 77 | 73 / 77 | 73 / 77 |
  | soprano semitone up | 47 / 51 | 60 / 64 | 60 / 64 |
  | soprano sixth down | 52 / 67 | 52 / 67 | 52 / 67 |
  | bass semitone + vibrato | 47 / 51 | 124 / 128 | 263 / 267 |
  | bass fifth + vibrato | 60 / 64 | 60 / 64 | 241 / 245 |
  | tenor semitone + vibrato | 44 / 48 | 124 / 128 | 263 / 267 |
  | tenor third + vibrato | 63 / 67 | 63 / 67 | 247 / 259 |
  | soprano tone + vibrato | 57 / 61 | 124 / 128 | 263 / 267 |

- **Reading:** the detector needs most of its 43 ms frame filled with the new note, and the 5-frame median adds two hops (21 ms), so a new pitch shows up 45–65 ms after the onset, the note 60 ms after it; an octave leap waits for the octave guard. With vibrato, a step of a tone or less is shown only after ~125 ms (a trough of the new note falls back into the hysteresis band of the old one), and the center needs most of its 300 ms window. Before browser overhead, the AGENTS.md budget (≤ 50 ms, aim 30 ms) is already exceeded by the core.

## 2026-11-09 – Lower latency: short window, 3-frame median, a new switching rule, center readiness

- **Short window:** while the current pitch has at least 4 periods in half a frame (≥ 187.5 Hz at 48 kHz, i.e. most tenor and all soprano notes), only the newest 1024 samples are analyzed (`TrackerConfig::short_window`, on by default; never shorter than 256 samples). The full frame is used again for a jump of more than 1.5 semitones, an unclear short window, the drone check, and every note below the limit. Short and full window agree within 0.15 semitone; leaps out of the short range show no octave errors (`core/tests/pitch_short_window.rs`).
- **Median:** 3 frames instead of 5 (one hop less delay). The octave guard (4 frames) still protects against octave errors, and the switching rule below takes over the anti-flicker role of the longer median.
- **Switching rule** (`PitchTracker::decide_note`): within 0.5 semitone of the shown note nothing changes; a jump of more than 1.5 semitones switches at once. In between (past the band of 0.5 + 30 cents hysteresis), the note switches at once when the current note is settled (steady for 3/4 of the center window), during the transit right after an onset or a leap (first 3 frames), or for a straight tone. When the note is swinging (its center history turned by ≥ 0.2 semitone down and up again, i.e. vibrato) or not yet settled, the pitch must stay past the band for `switch_dwell` frames (60 ms, 6 at 48 kHz) or its summed excess past the band must reach 0.3 semitone. A steady (not swinging) note also switches when its center has moved more than half a semitone after a third of the window. This fixes the two ignored voice tests (`bass_c4_vibrato_does_not_flicker`, `ascending_scale_each_note_settles`): wide vibrato (up to ±0.9 semitone at 4.5–6.5 Hz) never switches, while a held pitch past the midpoint is shown as the neighbor within 0.1–0.4 s (`core/tests/pitch_switching.rs`).
- **Center readiness:** `TrackedPitch::center_ready` (WASM slot 14, `PitchFrame.centerReady`, 15 fields) is true once the center can be judged: 3/5 of the center window is filled, or the last 6 estimates lie within 0.08 semitone (a straight tone). It latches until the note changes or the history resets. The cents gauge shows `data-zone="pending"` and the pitch curve draws in a neutral gray until then, so a note no longer starts red or yellow while the center is still catching up; the needle and readout keep moving. A test over 24 phases and several depths and rates checks that a ready center at a vibrato onset is never in the red.
- **`?debug`:** an overlay (and a console line every 5 s) with per-frame analysis time, frames dropped by the scheduler and `baseLatency`/`outputLatency`. Measured in headless Chromium: analysis 0.3 ms mean / 1.7 ms max per frame, no drops, baseLatency 10 ms, outputLatency 40 ms (44.1 kHz).
- **After** (same signals as the baseline; (d) is the time until `center_ready` and the zone shows):

  | step | (a) midi | (b) stable | (c) center | (d) ready |
  | --- | --- | --- | --- | --- |
  | bass semitone up (A2→B♭2) | 39 / 43 | 49 / 53 | 49 / 53 | 103 / 107 |
  | bass fourth down | 52 / 56 | 52 / 56 | 52 / 56 | 105 / 109 |
  | bass E2 → G2 | 49 / 53 | 49 / 53 | 49 / 53 | 103 / 107 |
  | tenor semitone down | 28 / 32 | 33 / 37 | 33 / 37 | 87 / 91 |
  | tenor third up | 47 / 51 | 47 / 51 | 47 / 51 | 100 / 104 |
  | tenor fifth up | 49 / 53 | 49 / 53 | 49 / 53 | 103 / 107 |
  | tenor octave up | 73 / 77 | 73 / 77 | 73 / 77 | 127 / 131 |
  | soprano semitone up | 25 / 29 | 33 / 37 | 33 / 37 | 87 / 91 |
  | soprano sixth down | 52 / 56 | 52 / 56 | 52 / 56 | 105 / 109 |
  | bass semitone + vibrato | 36 / 40 | 135 / 139 | 252 / 256 | 305 / 309 |
  | bass fifth + vibrato | 49 / 53 | 49 / 53 | 156 / 160 | 220 / 224 |
  | tenor semitone + vibrato | 25 / 29 | 124 / 128 | 241 / 245 | 295 / 299 |
  | tenor third + vibrato | 52 / 56 | 52 / 56 | 244 / 248 | 223 / 227 |
  | soprano tone + vibrato | 39 / 45 | 79 / 128 | 199 / 245 | 249 / 299 |

  `core/tests/pitch_latency.rs` asserts bounds on these: 60 ms for (a)–(c) on straight steps (80 for the octave), 150 ms for a vibrato step of up to 2.5 semitones, 300 ms for a vibrato center, readiness within 60 ms after (b) for straight tones and 330 ms for vibrato.
- **Trade-offs:** straight steps now show the note in 33–53 ms (was 57–67), high voices meet the 30 ms target for the raw pitch. The zone appears ~55 ms after a straight note change and ~180 ms after a vibrato one, on purpose. A semitone step with vibrato on a low voice is slightly slower than with the 3-frame median alone (135 ms vs. ~115 ms) because of the swing dwell, the price of the vibrato not flickering. The octave leap still waits for the octave guard. The TS mock engine reports `centerReady` but keeps the simple hysteresis rule. `process` stays allocation-free (`core/tests/pitch_no_alloc.rs` now also steps across the short-window limit).
- **Alternatives considered:** a dwell of 4 frames (wide 4.5 Hz vibrato flickered); a center switch after 4 frames (wide vibrato flipped back and forth); readiness at half the window (+25 cents at 4.5 Hz ±40 cents); a smaller frame overall (loses E2 and bass accuracy, hence the pitch-dependent short window); moving the analysis into the AudioWorklet (out of scope for now, saves message passing only).

## 2026-11-09 – SEO: meta tags, crawler files and a static fallback

- **Decision:** the single page carries everything crawlers and link previews need without running JavaScript:
  - **Head:** a descriptive Russian title and description, canonical link, Open Graph (`website`, `ru_RU` + `en_US`, a 1200×630 image), Twitter Card `summary_large_image` and `WebApplication` JSON-LD (free, any browser, music and education categories).
  - **Site origin:** one build-time value, `VITE_SITE_URL` (default `https://ktone.severnbli.dev`), resolved by the Vite plugin in `web/seo/site.ts`. It is exposed to `index.html` as `%VITE_SITE_URL%` and used to emit `robots.txt` (allow all, sitemap link) and `sitemap.xml` (the one page). The Docker build takes it as a build arg, so self-hosters can point canonical links at their own domain.
  - **Preview image:** `web/public/og-image.png`, generated by `scripts/make-og-image.py` from the brand banner with a Russian tagline (palette PNG, about 50 KB).
  - **Static fallback:** `#root` contains an h1, a short description, the feature list and a `<noscript>` note. An inline script adds a `js` class to `<html>` before the body is parsed, and CSS hides the fallback under it, so normal users never see it flash; React's `createRoot().render` then replaces it.
  - **nginx:** paths whose last segment has an extension are file requests and return a real 404 when missing (previously `/robots.txt` and `/sitemap.xml` returned `index.html` with 200); navigations still fall back to the SPA. Everything outside `/assets/` stays `no-cache`.
  - **Service worker:** `robots.txt`, `sitemap.xml` and `og-image.png` are not precached – the app never requests them.
- **Why:** crawlers without JavaScript (Yandex in many cases, Telegram/VK/Slack link previews) saw only `<title>kTone</title>` and an empty div. The fallback gives them the same text the app is about, and hiding it only when JavaScript runs is not cloaking: a JS-rendering crawler sees the real app, a non-JS one sees an honest description of it.
- **Alternatives:** SSR (needs a Node server instead of static nginx and a server-safe render of an app that is all microphone and canvas – not worth it for one page); build-time prerendering with a headless browser (heavier build, and the prerendered app UI is an idle "Start" screen with less useful text than the hand-written fallback); a `%VITE_…%` value in a committed `.env` file (works, but a typo would ship silently, while the plugin validates the URL and fails the build).
- **Left for the owner:**
  - Verify the domain in Google Search Console and Yandex Webmaster with DNS TXT records in Cloudflare, then submit `https://ktone.severnbli.dev/sitemap.xml` in both.
  - In Cloudflare, make sure Bot Fight Mode / Super Bot Fight Mode and any WAF rules allow verified bots (Googlebot, YandexBot, link preview fetchers such as TelegramBot), and that the "AI crawl" managed `robots.txt` option does not replace ours unless that is intended.
  - Check previews with the Facebook Sharing Debugger, Telegram's @WebpageBot and Google's Rich Results Test after deploy.

## 2026-11-09 – UI redesign: dark stage, one-screen layout, chips and sheets

- **Decision:** the web UI is a dark "stage" by default with a polished light theme. The theme follows `prefers-color-scheme` (dark when there is no preference) unless the user picks one in settings (`theme`: `system` / `dark` / `light`, applied as `<html data-theme>` before paint). All colors, spacing, radii and shadows are CSS custom properties on `:root` in `web/src/styles.css`, redefined once for light.
- **Color roles never overlap:** the brand accent (fuchsia `#c026d3` → violet `#6d28d9`, on the logo's deep indigo) is for chrome and selection only (Start button, selected segments and keys, focus rings, tonic line); accuracy uses mint / amber / coral (`--zone-*`, the logo's mint "hit" dot and coral note); out-of-key notes are sky blue. The logo itself is coral + mint on indigo, not a gradient – so the brand gradient lives in the UI chrome and the logo colors became the accuracy colors. Light theme zone colors are darkened to ≥ 4.5:1 on white; dark theme text is ≥ 7:1.
- **Accuracy is not color-only:** the gauge shows the needle position, tick marks and scale numbers at the zone edges, a center line, a big numeric readout with a check mark on a hit, and lights the «ниже» / «выше» side label when the vibrato center is off. The zones are a clean strip along the track edge instead of translucent fills (those mixed into muddy browns).
- **Layout:** the app is exactly one viewport tall (`100dvh`, safe-area insets): header (logo, key chip, clef chip, settings), then the stage – note + compact staff, full-width gauge, the pitch curve taking the remaining height, a labelled input level meter – and a bottom bar with the drone, a round Start/Stop and a disabled target slot (`FEATURES.target` in `web/src/features.ts`, a placeholder for the target-note feature). From 900×560 the stage is a grid: note | gauge | staff on top, a wide curve, the bar centered. An e2e test asserts no scrolling at 390×844, 360×640 and 1280×800 and ≥ 44 px touch targets.
- **Settings:** key and clef are header chips opening pickers (key: major/minor switch over a 3×5 grid ordered by key signature, 7♭ to 7♯ with C in the middle – a circle of fifths read in rows, usable at 360 px with 56 px cells; clef: list with clef signs). Everything else is a grouped sheet (Звук, Нотация, Точность, Интерфейс) with segmented controls and switches – a bottom sheet on phones, a side panel on desktop – with a light backdrop so detection stays visible. The drone has its own sheet from the bottom bar («Бурдон · до малой октавы»). Sheets are portalled modal dialogs that trap focus, close on Esc or a tap outside and restore focus.
- **Messages:** errors, the paused state with Resume, the level hints and the drone hints are toasts above the bottom bar (components portal them into the toast area).
- **Curve:** labels are placed by priority (tonic, dominant, mediant, rest) only where they fit 16 px apart inside the canvas; the line is drawn in runs of one zone color, each stroked wide and translucent, then thin and solid ("neon" without `shadowBlur`, fewer strokes than before). Measured in headless Chromium at 390×844 while listening: 60 fps with no frame over 25 ms, also with 4× CPU throttling, the same as before the redesign.
- **Accessibility:** only the note (not the 10 Hz frequency readout) is an `aria-live` region; the level meter's gate marker is explained by an info button and `aria-describedby`; `prefers-reduced-motion` turns off animations; system font stack only (works offline, no CDN).

## 2026-11-09 – Automatic noise gate

- **Decision:** the RMS gate is set automatically from the measured background noise, with no manual slider. `PitchTracker` (core) estimates the noise floor with **minimum statistics**: the quietest frame RMS over the last 1.5 s of *unpitched* frames, kept as 6 sub-window minima (fixed arrays, allocation-free). The gate is the floor + 11 dB, clamped to −60..−34 dBFS; until 0.5 s of unpitched frames have been seen it stays at `rms_threshold` (0.005, about −46 dBFS).
- **Never learning the voice:** a frame counts as pitched when the detector finds clarity ≥ 0.8 inside 70..1400 Hz – at any level, so frames below the gate are analyzed too (a soft voice or a hum is not noise). Pitched frames and the 0.3 s after them (note tails, reverb, breathy dips inside a note) do not advance the window and can only lower the floor. A sustained note therefore freezes the floor where the last pause left it. Any quieter frame lowers the floor at once; it rises only after a whole window (1.5 s) of louder unpitched sound.
- **API:** `PitchTracker::noise_floor() -> Option<f32>` and `gate() -> f32` (linear RMS, valid after every `process` call, pitched or not); `TrackerConfig` gains `auto_gate` (default on), `noise_window`, `noise_settle`, `noise_holdoff` (frames, sized by `for_hop`); `reset()` also forgets the floor. WASM: `Analyzer.noiseFloor` (0 while unknown) and `Analyzer.gate`. TS `Analyzer`: `noiseFloor: number | null`, `gate: number`; the TS mock ports the estimator (`web/src/engine/noiseFloor.ts`) and both engines run the same noise test. A device change creates a new analyzer, so the floor restarts there; so does an A4 change, which already called `reset()` in the WASM `configure`.
- **UI:** the meter's gate marker follows the live gate, a subtle band shows the floor (both hidden until known) and the info popover explains them. _Too quiet_ = no pitch, at least 4 dB above the floor and below the gate, for 1 s; unknown floor: no hint. A new _noisy room_ hint («Вокруг шумно – распознавание может пропускать тихие ноты») appears when the gate stays within 3 dB of its maximum (≥ −37 dBFS) for 3 s; it wins over _too quiet_, since noise swells in such a room would otherwise look like a quiet singer. The `ANALYZER_GATE_RMS` duplicate and the −60 dBFS floor guess are gone; only the gate bounds are mirrored in TS (checked against the real engine in `wasm.test.ts`).
- **Measured** (`core/tests/pitch_noise_gate.rs`, 48 kHz, hop 512): the floor is known 0.53 s after start; a −70 dBFS room (pink noise + 50/100 Hz hum) gives a −72 dBFS floor and the −60 dBFS minimum gate, and a −50 dBFS voice is pitched in 184/184 frames (it was below the old fixed −46 dBFS gate); a −45 dBFS room gives a −47 dBFS floor and a −36 dBFS gate with 0 of 372 noise frames pitched, and a −30 dBFS voice in it is pitched in 184/184 frames; white noise from −65 to −25 dBFS is never pitched; a 12 s note at −20 dBFS with breathy dips leaves the floor at −72 dBFS; a 200 ms clap does not move it; quiet → noisy reaches the maximum gate after 1.65 s, noisy → quiet falls back within one frame. Voice fixtures, drone, latency and no-alloc tests are unchanged.
- **Trade-offs:** the floor is a minimum, so it sits 1–2 dB below the mean noise level (the 11 dB margin accounts for it). Frames below the gate now run the detector (the same cost as a voiced frame, so the worst case per frame is unchanged). A steady tonal noise in range (a loud hum, a fan whine with clear pitch) is "pitched" and never trains the floor – the gate stays where it was, and such a tone above it may show as a note, as before. Singing without any pause from the very start keeps the default gate until a breath gives 0.5 s of unpitched audio.
- **Alternatives considered:** a manual sensitivity slider (rejected by the user); an exponential average of unpitched frames with fast attack / slow release (follows the mean, so a single loud stretch drags it up and its release time trades against recovery); a fixed calibration at start (breaks when the room changes, and the user may start singing at once); a percentile over a stored history (needs a sort or a histogram per frame for no gain over sub-window minima).
